# Formal mathematics (Lean 4)

This is the **F — Formal mathematics** strand of the Lumenary: a small Lean 4 library of
definitions and machine-checked proofs that the website shows next to human-written lessons,
plus Lean exercises for learners.

> **Honest scope.** Everything here uses **core Lean 4 only** (toolchain
> `leanprover/lean4:v4.35.0`). There is **no Mathlib and no Batteries** dependency yet;
> Mathlib integration is planned. Where Mathlib has an analogous notion, the docstrings say
> "Mathlib analogue: …" as a pointer for learners. Those pointers were **not** checked
> against Mathlib — nothing in this project imports it.
>
> A declaration counts as *formally verified* only if `scripts/verify-lean.mjs` built it
> successfully in a real run and its `#print axioms` output contains no `sorryAx`. The
> generated report `content/verification/lean-report.json` is the single source of truth;
> the website derives the "formally verified" label from it and never from hand-written
> frontmatter.

## Layout

```
formal/
  lean-toolchain           leanprover/lean4:v4.35.0
  lakefile.toml            package `lumenary`; libraries `Lumenary` and `LumenaryExercises`
  lake-manifest.json       generated by Lake (no dependencies)
  Lumenary.lean            imports every module below
  Lumenary/
    Collections.lean       lists as collections ("for grown-ups" peek at the K–2 lesson)
    Sets.lean              sets as predicates, ∪ ∩ ᶜ ∅ univ ×ˢ, De Morgan
    Integers.lean          additive inverses, rules of signs, units of ℤ
    Modular.lean           clock arithmetic, inverses mod n, congruence as an equivalence
    Functions.lean         injective / surjective / bijective, graphs of functions
    Composition.lean       ∘ is associative, has identities, preserves injectivity etc.
    Category.lean          minimal categories, types as a category, monoids and groups,
                           the product universal property in types
  LumenaryExercises.lean   imports every exercise file
  LumenaryExercises/       statements with `sorry`; solutions live in `Lumenary`
scripts/verify-lean.mjs    builds, inspects axioms, writes the report
content/verification/lean-report.json   generated — never edit by hand
```

## Installing and building

### With elan (recommended for contributors)

[elan](https://github.com/leanprover/elan) reads `formal/lean-toolchain` and fetches the
matching Lean release automatically:

```sh
cd formal
lake build                               # both libraries (the default targets)
lake build Lumenary LumenaryExercises    # exactly what the verify script runs
```

### With the official release archive (as used to produce the current report)

No elan is needed. Download the official Lean 4.35.0 release for your platform from
<https://github.com/leanprover/lean4/releases/tag/v4.35.0> and extract it so that the
binaries end up in `.toolchain/lean-4.35.0-<platform>/bin/` at the repository root (the
`.toolchain/` directory is git-ignored). Then either put that `bin` directory on your `PATH`
or just run the verify script, which finds it on its own.

### Verifying and regenerating the report

```sh
npm run verify:lean                  # = node scripts/verify-lean.mjs
node scripts/verify-lean.mjs --clean # `lake clean` first, then a full rebuild
LEAN_BIN=/path/to/lean/bin node scripts/verify-lean.mjs
```

The script looks for `lean` and `lake` in this order: the directory in `$LEAN_BIN`;
`<repo>/.toolchain/lean-*/bin` (preferring the version named in `lean-toolchain`);
`~/.elan/bin`; `$PATH`. It then

1. runs `lake build Lumenary LumenaryExercises` in `formal/` and times it;
2. parses the region markers and declarations in every `formal/**.lean` file;
3. writes a temporary `formal/.lake/verify/PrintAxioms.lean` that imports the modules that
   built and runs `#print axioms` on every main-library declaration (via `lake env lean`);
4. records the sha256 of every source file and writes
   `content/verification/lean-report.json` (schema: `LeanReport` in `src/lib/schema.ts`).

The report is written **even when the build fails** (with `build.success: false`); the
script then exits 1. It also exits 1 if any main-library declaration depends on `sorryAx`,
if an exercise produces a warning other than "declaration uses `sorry`", or if the region
conventions below are violated. If a file did not build, its declarations are reported with
`usesSorry: true` and empty `axioms` (Lean's error recovery elaborates failed proofs to
`sorryAx`, and in any case nothing unbuilt may be labelled verified), and files that import
it are reported as `success: false` too.

## Conventions

The website extracts Lean source **by region id** and shows it to learners, so code should
be readable and idiomatic, with a short teaching docstring on every declaration.

```lean
-- @region sets.inter_subset_left
-- @provenance independent
/-- `A ∩ B ⊆ A`: whatever is in both sets is, in particular, in the first one. -/
theorem inter_subset_left (A B : Set α) : A ∩ B ⊆ A := by
  intro x hx
  exact hx.1
-- @endregion
```

* **Region ids** are lowercase and dotted: `<module>.<name>` (e.g. `sets.compl_inter`,
  `modular.mod_eq` for `ModEq`); exercises use `ex.<module>.<name>`. Ids are unique across
  the project and use only `a–z`, `0–9`, `_` and `.` (so `Monoid'` lives in region
  `category.monoid`).
* **One declaration per region.** Notation commands (`scoped syntax`, `scoped infixr`, …) sit
  between regions.
* **`@provenance`** is required on every main-library region:
  * `library` — the proof *applies an existing library theorem* (here: core Lean's), e.g.
    `neg_mul_neg_library := Int.neg_mul_neg a b`;
  * `independent` — proved here from more basic facts (it may still use small library
    lemmas as steps, e.g. `Int.mul_add` in `neg_mul_neg_from_axioms`). Proofs by `rfl` or
    `decide` count as independent: the kernel checks the computation directly;
  * `definition` — a `def`, `structure`, `class` or `instance`; there is nothing to prove.
* **`@solution <Declaration>`** on every exercise region names the solved declaration in the
  main library (checked by the script).
* Instances are always **named** (`instance instUnion : Union (Set α)`) so they can appear in
  the report. `axiom` declarations are forbidden.
* `autoImplicit` is off (Mathlib's convention): every variable is declared.
* Prefer structured proofs (`intro`, `exact`, `constructor`, `cases`, `calc`, `obtain`) over
  opaque automation; `decide`/`rfl`/`omega` are fine for small concrete facts.

### Reading the axioms column

`#print axioms` lists the axioms a declaration depends on, **transitively through every
library lemma it uses**:

* `propext` (propositional extensionality), `Quot.sound` (from which function
  extensionality `funext` is derived) and `Classical.choice` (classical logic, excluded
  middle) are Lean's standard axioms. Many core `Int` lemmas are themselves proved with
  `simp`, which is why almost every integer result shows `propext`.
* `Classical.choice` marks genuinely classical reasoning: compare `sets.compl_union`
  (constructive) with `sets.compl_inter`, which needs excluded middle.
* `sorryAx` would mean an incomplete proof. It appears nowhere in the main library.

## Known limitations

* Core Lean only; no Mathlib, so no `ring`, `simp` sets for sets, `fin_cases`, etc. Some
  statements that Mathlib states for every ring are stated here for `Int` only.
* `Category` is deliberately minimal (no functors, no `⟶`/`≫` notation, no opposite
  categories). `typesCategory` is the category of Lean *types*, the type-theoretic analogue of
  **Set**, not a category of ZFC sets.
* Concrete numeric facts (`modular.*`, `collections.order_matters_for_lists`) are checked by
  `decide`, i.e. by evaluation in Lean's kernel.
* Checking relies on Lean's kernel as run by `lake build`; no independent re-checker
  (e.g. the `leanchecker` shipped with the toolchain) is run yet.
* The website shows source by region; it does not run Lean in the browser. Learners who want
  to try the exercises need a local Lean install (see above).
